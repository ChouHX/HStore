## 推送前修掉的 .gitignore 坑

原 `.gitignore` 第一条是 `dist/`，会把 `backend/web/dist/` 整目录忽略，
**连 `backend/web/dist/index.html` 占位文件一起**。结果是全新克隆后
`go:embed all:dist` 找不到目录，`go build` 直接失败。

改为：
```
/dist/                     # 只忽略根目录的 vite 旧产物
backend/web/dist/*         # 只忽略 dist 内容
!backend/web/dist/index.html
```
`backend/web/dist/*` 不排除目录本身，否定规则才能生效（若父目录被排除，`!` 无效）。

## 兑换码改为「码即凭证」，取消归属校验

### 原因
后台批量生成的兑换码不记录归属（`redeem_codes` 虽有 `used_by`，但只是核销记录，不是所有权）。
原实现要求 `row.UsedBy == uid`，导致别人核销过的码换个账号就取不了件，与业务模型不符。

### 改动
- `service/mailbox.go`：`resolveOrder` → `resolveTarget(uid, code, orderNumber, isAdmin)`
  返回 `(order, viaCode, msg, ok)`。
  - 兑换码路径：**不做任何归属校验**，匿名也可用（码就是凭证）。
  - 订单号路径：仍要求登录 + `order.UserUID == uid`（或 admin）。
  - 输入先按兑换码查，查不到且已登录时**再按订单号查一次**——上游订单号格式不固定，
    可能长得和兑换码一样，不该让用户卡在前端的格式猜测上。
  - 新增 `looksLikeCode()`：16 位字母数字，分隔符可有可无。
- `service/redeem.go`：旧的 `Pickup`（`POST /api/pickup`）改为复用 `resolveTarget`，
  规则统一，不再有第二套判定。
- `store/redeem.go`：新增 `NormalizeCode()`，`GetCodeByCode` 用它查库，
  所以 `testcode0001aaaa` / `TESTCODE0001AAAA` 都能命中 `TEST-CODE-0001-AAAA`。
- `src/pages/PickupPage.tsx`：`looksLikeCode` 放宽为「去分隔符后 16 位字母数字」，
  新增 `normalizeCode` 补横线；提示文案补「兑换码不绑定账号，谁持有谁就能取件」。

### 验证（临时库 + 单文件二进制 PORT=3057，码属于 uid=9）
- demo(uid=2) + 他人码 → 不再报「不是你的」，直接走到 OAuth（假 token 被微软拒，符合预期）
- demo + `testcode0001aaaa`（无横线小写）→ 同样命中，说明 NormalizeCode 生效
- demo + 他人订单号 → `无权查看该订单`（订单号仍校验归属）
- demo 把订单号填进 code 框（15 位）→ 回退到订单号路径，`无权查看该订单`
- 匿名 + 码 → 通过；匿名 + 订单号 → `未登录只能用兑换码取件`
- 匿名 + 不存在的码 → `兑换码不存在`
- `POST /api/pickup`（旧接口）+ 他人码 → `取件成功`，与邮箱取件行为一致
- `go build` / `go vet` / `tsc --noEmit` 全过；`build:all` 20.3MB

## 支付宝支付后卡死 + 联系方式必填 + 公开订单查询

### 根因（支付后卡死 / 不发货）
1. **游客履约永远失败**：`FulfillGuestPurchase` 调 `PlaceOrder(Payment:"balance")`，
   而游客账户余额恒为 0 → 每次都 `余额不足`。线上库里 guest_purchases #3 就是这个错。
   改为 `Payment:"external"`（钱已通过支付宝/USDT 收到，不再扣余额）。
2. **同步网络调用放在 HTTP 请求里**：`GET /api/guest/order` 每次都同步查支付宝账单 + 上游下单，
   单个请求可能 30–50s；前端 `setInterval` 4s 一次 → 请求叠加到浏览器 6 连接上限 → 整页卡死。
   改为 `syncGuestPurchaseAsync()`：后台 goroutine、45s 超时、按订单 ID 去重，HTTP 立即返回。
3. `QuickCheckAlipayOrder` 补 10s 硬上限 + 分页循环里检查 `ctx.Err()`（原来最坏 100 页 × 15s）。
4. 前端轮询改链式 `setTimeout`（上一次回来才排下一次），彻底避免叠加。

### 联系方式必填
- `orders.contact` / `guest_purchases.contact`（`addColumns` 迁移 + 索引）。
- `service.ValidateContact()`：非空、≤64 字符、无控制字符；`/api/order/create`、`/api/guest/order` 都校验。
- 弹窗预填顺序：上次填过的 → 账号 phone → 账号 email。

### 公开订单查询 `/orders`
- `GET /api/orders/query?keyword=`：订单号精确匹配 或 联系方式精确匹配（邮箱忽略大小写），
  结果合并 `orders` 与未进入 orders 的 `guest_purchases`（按上游订单号去重），最多 100 条。
- `GET /api/orders/query?orderNumbers=a,b,c`：本机记录批量回填（最多 50 个）。
- `GET /api/orders/query/detail?orderNumber=&contact=`：**双重匹配**才返回卡密。
- 限流 `allowQuery()`：60 次/分钟/IP。
- 前端 `src/pages/OrderQueryPage.tsx`：卡片列表 + 10 条/页 + Drawer 详情；
  `lib/orderStorage.ts` 把订单号存 `hstore:orders`（≤50 条），进页面自动回填。
- 新增 `src/pages/GuestPayPage.tsx`（`/g/:token`）：关掉购买弹窗后游客仍能继续扫码/看卡密。

### 服务器现状（排查时记录）
- `opcuu.com` → openresty → `127.0.0.1:3001` → 容器 `hstore`（`/root/api/shop`，data 挂载 `/data`）。
- `ccmtc.cfd` → 5002 是另一个 Redeem 项目，别搞混。
- 容器当时是**手动 stop**（ExitCode=0、非 OOM）；WAL 4MB 是异常退出留下的。
- 本机 curl 访问 127.0.0.1 要走 `--noproxy '*'`。
